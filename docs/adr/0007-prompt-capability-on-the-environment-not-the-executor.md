# The prompt capability is carried by the ENVIRONMENT, checked PER-CAPABILITY

The interactive unknown-signer resolver needs to ask a human to paste a transaction hash. The obvious place to hang that ability is the executor, because that is where a `PromptExecutor` is already in scope (`createExecutor` takes one). We deliberately did NOT do that.

The seam that needs the capability lives in `createEnvironment`, and there are THREE callers of it: the one inside `createExecutor`, where a prompt is in scope; `loadEnvironmentFromStore`, where there is none; and the shared test harness in `@rocketh/test-utils`. **hardhat-deploy reaches the environment through the second**, via `@rocketh/node`'s `loadEnvironmentFromFiles`. Threading the capability through the executor alone would therefore have silently pinned every hardhat-deploy user to the non-interactive policy forever, with no error and no way to opt in. So the capability is carried on `ExecutionParams` (and its resolved form) and reaches the environment on every construction path. This is the road `autoImpersonate` already travels successfully, for exactly the same reason.

The capability is checked **per-CAPABILITY (is there a text-prompt method?), never per-executor (is there a prompt object?)**. `@rocketh/web` ships a `PromptExecutor` whose confirm implementation returns `{proceed: true}` without asking anyone, so mere presence proves nothing: an executor can exist and still be incapable of, or dishonest about, asking a human. The text ability is therefore an OPTIONAL method whose ABSENCE is the signal, which also keeps the widening purely additive (no existing implementation breaks) and avoids a separate capability descriptor that could drift from what the object can really do.

## Consequences

- `'auto'` resolves to `'ask'` only where a text prompt genuinely exists, and to `'throw'` otherwise, so CI and the browser can never hang. A per-call override may vary the policy but cannot exceed capability: capability is a ceiling, not a default.
- `@rocketh/web` deliberately does not implement the text variant. The browser answer for a fork or dev node is **impersonation, not interactivity**: declare the unsignable addresses as NAMED accounts and enable `autoImpersonate`, which resolves them BEFORE the seam so no policy is consulted at all. Three constraints make that route work and none may be softened in documentation: only NAMED accounts are impersonation candidates (an unnamed account or a bare `from` is never impersonated); it requires a node implementing the impersonation RPC, so against a real chain the account stays unsignable and correctly lands on throw-and-defer; and `autoImpersonate` is RUN-level, not per-transaction.
- Because the capability rides `ExecutionParams`, the shared test harness needs no new API to inject a fake prompt: its existing partial pass-through is enough. A task that finds itself adding a harness option should treat that as a signal the plumbing regressed.
- This is orthogonal to ADR 0006. `autoImpersonate` remains a NODE CAPABILITY resolved before the seam and `onUnknownSigner` remains the POLICY afterwards; adding a prompt capability does not blur that boundary and introduces no `'impersonate'` policy value.
