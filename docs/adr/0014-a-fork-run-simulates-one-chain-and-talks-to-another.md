# A fork run SIMULATES one chain and TALKS TO another, and only the first is inherited

rocketh has been able to run against a fork since hardhat-deploy's `HARDHAT_FORK` existed, but core never knew it was on a fork of anything: `fork` was set from `typeof environmentProvided !== 'string'`, so it meant "the environment was not given as a string" and an ordinary in-memory run was flagged as a fork. `fork-of-a-named-network` makes the flag say WHICH network. This ADR records the model that fell out of doing so, because three of its parts are surprising and one of them was a live bug.

**What `{fork: X}` fundamentally means: be `X` for deployment RECORDS, while not being `X` for chain IDENTITY.** This is not how it reads, so it is worth the sentence. The evidence is that everything else a fork run does is already reproducible without the fork mechanism: an ordinary environment declared as `{chain: 1, overrides: {rpcUrl: 'http://localhost:8545'}}` gets the right chain id, mainnet's settings, a local connection and a passing identity check. The one thing it cannot do is read mainnet's deployment records, because records live under the environment NAME. That is the whole job, and it is why `context.fork` is consulted at exactly one load-time site, to skip the chainId/genesisHash check when loading a folder that belongs to another chain.

**A fork run therefore has TWO chain identities, and conflating them is what made the previous behaviour wrong.**

- The **simulated** chain is the network being forked. It drives the configuration lookup, the deployment records, the deployment semantics and the policy. "This is a fork of mainnet" is a statement about this one.
- The **connected** chain is whatever the node actually reports. It drives the `chainId` field of every transaction rocketh builds, and it is what the chain-identity check must be lenient about.

The connected identity cannot be wished away, because a transaction's chain id is consensus-level: for a locally signed transaction (`signerOnly`, which is what the `privateKey` protocol returns) the id is committed to in the signature, and a node rejects a mismatch. And the two genuinely differ by tool, measured rather than assumed: **anvil** forking mainnet reports chain id 1, while **hardhat** reports 31337, because `resolveEdrNetwork` defaults `chainId` to 31337 and the forking config never feeds it. Both are legitimate; neither is a misconfiguration; and a rule that adopts the simulated id for transactions would break every hardhat-deploy user, while a rule that adopts the connected id for configuration is what produced the bug below.

**The bug this fixes, which nobody had hit:** `env.network.chain` was built from `chains[31337].info`, whose `id` is the id it was asked for, and `execute` and `tx` hex-encode `env.network.chain.id` into the transaction. So every fork run declared chain 31337 regardless of the node. It was invisible because the only caller able to fork was hardhat, which also reports 31337. It was a trap laid precisely where the `--fork` CLI path will step, since that path exists to attach to anvil.

**The chain-config lookup SPLITS rather than swaps.** `idToFetch = fork ? 31337 : chainId` was half right and the half that was right is easy to delete by accident: `actualChainConfig` supplies the provider, so sending the lookup to 31337 is exactly what points a fork run at the local fork instead of at production. What was wrong is that the same lookup also supplied the deployment semantics and policy. So connection comes from the local side, semantics from the forked network. "Resolve the chain config from the forked network" would break the thing that works.

**Where the SIMULATED chain id comes from, and why declaring it is NOT required.** It is needed for exactly one thing: keying `chains[<id>]` to inherit the forked network's settings. Not for deployment records, which are keyed by the environment NAME; not for transactions, which use the connected chain; not for the identity check, which simply does not compare when nothing is declared. Three sources, in order:

1. **Supplied with the fork input** by whoever constructed it. hardhat-deploy has the forked network's own config and already carries a commented-out probe that fetches its `eth_chainId`, which is the reliable case. The CLI side is weaker than it first appears: `@rocketh/node` does hold a name-to-chain map, but it is keyed by `kebabCase(chain.name)` from viem, so mainnet's key is `ethereum`, not `mainnet`, while an environment name is whatever the user chose. Name resolution therefore works only by coincidence and must not be relied on as the mechanism. Core cannot do it at all: the map is on the wrong side of the dependency edge (`@rocketh/node` depends on `rocketh`, and `rocketh` has no viem dependency).
2. **`environments[<name>].chain`**, when declared. Also where a fork's overrides live.
3. **The id the run already computed**, which is the provider's. A non-fork run works this way today and needs no `environments` entry at all, which is precisely why nothing in this repo declares one.

Step 3 is what makes zero configuration work, and it is not a conflation of the two identities: **anvil forking mainnet reports 1 because it is forking mainnet**, so the connected id genuinely IS the simulated one, arrived at honestly. Only hardhat breaks the coincidence by reporting 31337 while simulating mainnet, and there the fallback lands on exactly today's behaviour rather than on something worse. That case is what step 1 exists to fix, in the caller that has the information.

**The DESCRIPTOR, though, asserts only what it knows.** Its chain id is present when the id came from step 1 or 2, and absent when the run merely fell back to the provider's, because under hardhat that number is the local engine's and calling it "the network being simulated" would be a lie told to every later consumer (the dry run and the transaction capture both branch on it). Same instinct as ADR 0012: a record asserts what was established, not what was assumed. The semantics lookup may use the fallback; the descriptor may not claim it.

**Configuration is INHERITED from the forked network, and a fork states only what differs.** The difference lives in a `whenForked` sub-key on that network's own environment entry, layered `chains[<forked id>]` under `environments[<name>].overrides` under `environments[<name>].whenForked`, most specific last, applied only when the run is a fork. It is spelled `whenForked` rather than `fork` deliberately: `fork` reads as an imperative, and a key that reads as an imperative invites exactly the misreading the next paragraph has to argue against. A conditional name cannot be read as a command. Half of that layering already existed: the environment-override layer already ran on fork runs, because the environment name IS the forked network's name. Only the chain bucket beneath it was wrong.

The rejected alternative is worth keeping, because it is cheaper and will be proposed again: a conventional environment key, `"<network>:fork"`. It needs no new type at all. It loses on one edge that no amount of documentation removes: it reads as a NAME, the obvious implementation makes it one, and at that moment the fork reads and writes a `mainnet:fork/` deployments folder and forfeits the only thing forking is for. The environment name reaches `path.join(deploymentsFolder, environmentName)`, and a colon is a reserved character on Windows besides. Same reasoning that replaced `pushUnknownSignerPolicy`/`popUnknownSignerPolicy` with a single scoping verb: prefer making the mistake unrepresentable over documenting the pairing.

**Declaring `whenForked` configuration does NOT put a run into fork mode.** A run is a fork because of how it was invoked. If the presence of configuration were the switch, a user who described their fork once would find every later run forked. The name is chosen so this sentence is a reminder rather than a defence.

## Naming: the CLI flag is `--is-fork`, and `--fork` is reserved for the day we can honour it

The standalone-user flag is named twice in the planning notes as `--fork`, and that name promises something rocketh cannot do. **`--fork` reads as an imperative**: fork it. rocketh does not fork anything; it ATTACHES to a node somebody else forked, and it will only be able to honour the imperative if an in-process engine lands, at which point it would need somewhere to fork FROM and a block to fork AT. So the attach flag is `--is-fork`: an assertion about the node being pointed at, which is exactly what the user is telling us.

That also leaves the two verbs able to coexist honestly later: `--is-fork` attaches to an existing fork, and a future `--fork` creates one. Naming the attach flag `--fork` today would force the create flag to be named around it tomorrow.

This is the second naming correction of the same shape in this decision, after `whenForked` (which was `fork`), and the repetition is the useful part: **in this domain the bare word `fork` is ambiguous across three parts of speech** — the noun (a forked node), the adjective (this run is against one) and the verb (create one). Every name that uses it should be explicit about which it means, because the verb reading is the one that silently promises a capability.

## Refinement: the `overrides` layer lends a fork everything EXCEPT its endpoint

The layering above is stated as `chains[<forked id>]` under `environments[<name>].overrides` under `environments[<name>].whenForked`, most specific last. That is right for every field but one, and the exception was found by building it: `overrides` belongs to the environment of a REAL network, so its `rpcUrl` is **that network's own endpoint**. A fork run inheriting it dials production while the user believes they are on their fork, and does so silently, with the deployment records and every impersonated Safe step landing against the real chain. It is the same failure the `chains[31337]` correction above prevents, arriving one layer higher.

So on a fork the endpoint is **withheld** from the `overrides` layer, and comes from `whenForked.rpcUrl` else the conventional local endpoint. Every other field in that same bag still crosses, so a fork keeps being configured like the network it simulates.

This is not an exception to the model, it IS the model: connection from the LOCAL side, everything else from the network being SIMULATED. The endpoint is the connection, and the connection may not be inherited from the simulated network at ANY layer, which is exactly why `chains[<forked id>]` never supplied it either. Writing `whenForked: {rpcUrl}` was already the documented remedy, but a remedy nobody knows they need is not a defence: same reasoning as `whenForked`'s own naming, prefer making the mistake unrepresentable over documenting the pairing.

The hazard was latent rather than live when it was closed, because the only caller that could fork (hardhat-deploy) always passes a `provider`, which beats any `rpcUrl` in the merge. It becomes reachable on the `--is-fork` path, which is precisely the path that attaches to an anvil fork with no provider of its own, so it was closed before that path exists rather than after.

## Refinement: a fork does not SAVE unless asked, and core is where that is said

The consequence below deliberately left saving alone, and it is now closed. The environment NAME being the forked network's is right for READING and wrong for WRITING: core defaulted `saveDeployments` to `true` for every name except `memory`, `hardhat` and `default`, so a fork of mainnet defaulted to writing into `deployments/mainnet`, and `context.fork` was consulted on no write path at all. Nothing was corrupted, because the only caller able to fork paired its fork input with `saveDeployments: false` ITSELF, which is exactly the shape this decision keeps refusing elsewhere: the knowledge that two things must be passed together living in the caller rather than in the thing being configured. So **a fork now implies `saveDeployments: false`**, stated once in `resolveExecutionParams`, and the plugin's pairing was deleted rather than kept as a belt.

The term sits ABOVE both existing default branches, not inside the named-environment one, because the default short-circuits to `true` when there is no provider, and a fork with no provider is precisely the `--is-fork` case (attach to an anvil fork by rpc url). A rule placed on the name branch alone would have missed the one path it exists to protect.

An EXPLICIT `saveDeployments` still wins, since it is read before any default. That direction is the reachable one and it has to stay expressible, and it is also the right shape for the CLI: `--save-deployments` is set-only with no `--no-save-deployments` counterpart, so on a fork the flag is the only way to turn saving ON once the default is off.

There is deliberately no fork-saves-elsewhere destination. If a fork run should ever save somewhere other than the forked network's folder, that is a separate decision, and nobody needs it yet; this makes the default safe without inventing one.

## Consequences

- **`chains[31337]` stops being the fork run's configuration.** It is where a user configures their LOCAL DEV NODE, and all of it, tags included, was silently becoming the configuration of a fork of mainnet. Deploy scripts branch on tags, so a script taking a shortcut under a `local` tag was taking it during what the user believed was a mainnet rehearsal. That is worse than absent configuration, because it is different configuration actively applied.
- **`autoImpersonate` defaults ON for a fork**, since impersonation is what makes Safe-owned steps executable and a fork is where rehearsing them is the point. It stays an explicit switch, so `false` still wins and the deferral path remains testable on a fork (ADR 0006 keeps impersonation and the unknown-signer policy orthogonal, and this does not blur that).
- **Saving is deliberately NOT changed here.** Core would still save a fork run into the forked network's folder, and the only caller that can fork guards it in the caller. That is a real trap for the future `--fork` path, and it is deliberately left to the standalone-user track rather than folded in. (Closed since, on that track: see the refinement above.)
- **The descriptor is shaped to grow a CREATION half.** Today rocketh ATTACHES to a fork somebody else started, so the block to fork from is not its to choose. When an in-process engine lands it will CREATE forks and need EDR's `ForkConfig` fields; the url needs no new configuration, because the forked network's rpcUrl is already in the config this model teaches the run to read.
