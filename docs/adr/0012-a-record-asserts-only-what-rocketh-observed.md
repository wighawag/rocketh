# A persisted record asserts only what rocketh OBSERVED, never that a step happened

Idempotency in rocketh is on-chain-state-driven (ADR 0006). The question that keeps coming back, in two forms, is whether a run can instead REMEMBER that a privileged step is done so a later run skips it: the script-level form exists today (`func.id` plus `return true` writes `.migrations.json` via `recordMigration`, `packages/rocketh/src/executor/index.ts:552-557`), and a per-`execute` form was proposed and is REJECTED here. The rule that settles both: **a record can only ever assert what rocketh observed, and rocketh observes a step only when it sees the transaction land.**

Walk the three outcomes of the unknown-signer seam against that, because the whole question turns on the case where the transaction is executed by somebody else.

- **`ask` OBSERVES.** rocketh did not send the transaction, but it verified inclusion and success before saving anything, held a deployment to the stricter `requireDeployedContract` standard, and ranked the evidence that the pasted hash is the call it asked for (`classifyPastedTransaction`, tiers `direct` / `account` / `embedded` / `none`, `packages/rocketh/src/environment/pastedTransactionIntent.ts:50-126`). A record written on this path would be SOUND. An earlier framing of this decision said "rocketh sent it", which was wrong: sending is not the criterion, observing is.
- **`throw` OBSERVES NOTHING, and fails closed.** The error propagates out of `deployScript.func(...)` (`packages/rocketh/src/executor/index.ts:545`), the run aborts, and line 552 is never reached, so nothing is recorded. The operator executes out of band, re-runs, and the script converges only because its steps are chain-guarded.
- **A CAUGHT deferral observes nothing and does NOT fail closed.** Under `catchUnknownSigner` (and under any collector built on it) the script survives the deferral, keeps going, and can still reach `return true`. The executor then records the id and the next run skips the WHOLE script, including the step that never happened, silently and permanently. This is the shape two production DeFi teams described using in v1 (the deployment field study behind the EF grant application: wrap each privileged call, keep going, write the transactions to JSON, propose the Safe batch from a `runAtTheEnd` script), so it is not hypothetical.

Soundness under `ask` is nonetheless not enough to promote a record to source of truth, and this is the load-bearing half of the decision. `auto` resolves to `ask` only where a human can be reached and degrades to `throw` where one cannot (ADR 0007). So the same script, on the same chain, under the same policy, writes the record on a developer's terminal and does not write it in CI. Persisted state whose existence depends on whether stdin was a TTY is worse than no persisted state, because the CI run then diverges from the dev run in a way nobody predicts from reading the script.

**Therefore: the chain-derived guard is the correctness mechanism, and any record is at most an optimisation layered in front of it.** That is already true of the script-level `id` today, which self-heals only BECAUSE the steps under it are chain-guarded: remove the guard and run 2 defers again, the id is never recorded, and the loop never closes. There is no version of this that works without the guard, which is why the guard is being made first-class on `execute` rather than left as a hand-written `read`-then-`if` at every call site.

## Considered options

- **A `'collect'` (or `'defer'`) value on `UnknownSignerPolicy`,** letting a run continue past every unsignable step and accumulate the transactions for one Safe batch at the end. REJECTED on the seam's return contract: the seam sits inside `broadcastTransaction` and must return a real transaction hash so the normal pipeline (`savePendingExecution` / `waitForTransaction`) takes over, which is how `ask` returns and why `throw` returns not at all. `collect` can do neither, so it would have to fabricate a hash, a receipt, and for a deploy an address for a contract that does not exist, which then flows into `env.save`. That is a second execution model (a plan / dry-run mode) wearing the union's clothes, not a fourth value in it. It would also apply "this step did not happen, continue anyway" to calls no author opted into, where today that acceptance is per-call and explicit (you wrote the wrapper). The batching need behind the request is real and is served instead by a collector wrapper over `catchUnknownSigner` plus a `runAtTheEnd` consumer, both already expressible, which keeps it out of core (`work/specs/ready/explore-unknown-signer-adapters.md`).
- **An `id` on `execute`, recorded on confirmed inclusion.** REJECTED for the capability-conditional reason above. Not wrong, merely unreliable in exactly the situation it is wanted for: in a Safe-owned or governance-owned system the privileged calls are precisely the ones rocketh does not send, so the record is populated only on the interactive path and only when a human was present.

## Consequences

- **Double execution is a real hazard under `throw` with no guard, and nothing warns about it today.** rocketh prints the transaction, aborts, records nothing; the operator executes it; the re-run surfaces the identical transaction again because rocketh has no way to know. For an idempotent setter that is a wasted round trip. For a non-idempotent privileged call (a mint, a transfer, an increment, a governance action carrying its own nonce) it is a loss. This is inherited from hardhat-deploy v1 unchanged and has never been written down.
- **`return true` must never be reached on a path where a step was deferred and caught.** See the amendment below for how this is handled.
- **The pasted hash has no recency check**, only the evidence classifier, so a hash from a transaction executed after a PREVIOUS run is accepted. That makes `ask` a supported recovery from a stale `throw`, and it is currently undocumented.
- `ask` is the only policy on which deferral and the migrations feature coexist correctly, which is an argument for it remaining the default wherever a human can be reached.

## Amendment (2026-08-27): the migration hazard is DOCUMENTED, not enforced, and "persist nothing" was being over-read

Two corrections to what the consequences above implied. Both were reached by pushing on the design rather than by new information, and both make the codebase smaller.

**Enforcement was rejected.** The consequence above proposed that the executor refuse to record a migration for a script that deferred. Successive drafts grew that into a public script option (`deferralIsCompletion`), a per-script deferral mark, and a change to when `.migrations.json` is written. It is all cancelled (`work/tasks/cancelled/refuse-migration-record-when-a-script-deferred.md`). The argument that kills it: `catchUnknownSigner` is a try/catch, and a user who writes their own `try {} catch {}` and returns `true` produces an identical outcome with none of the machinery. Policing our wrapper while the plain-language equivalent goes unpoliced taxes the user who reached for the supported tool and stops nobody. This is the same reasoning that made the `execute` guard optional rather than mandatory, and it should be applied consistently. `return true` with an `id` is a claim the author makes about their own script, and rocketh has no better information about it than they do. The hazard is real and is documented instead.

**"Nothing is persisted" is a property of the SEAM, not a prohibition on the project.** The phrase has been repeated often enough across these documents to start reading as a ban, and it was applied that way while designing the deferred-transaction collector, which pushed the collection in-memory, which made a halted run lose the batch, which is what made the enforcement above look necessary. ADR 0006's actual sentence anticipates the opposite: "a persisted batch, if ever built, belongs downstream in a consumer package, not in the core seam". `unknown-signer-v1-migration` requires that persistence be OPT-IN so a migrated v1 script is unaffected; it does not forbid it. What the doctrine protects against is a record acquiring AUTHORITY, meaning something consulted to decide whether a step is needed, which this ADR shows is systematically blind in the governance-owned case. A write-only artifact is not that. `deferred-transaction-collector` therefore writes the collected transactions to an opt-in file, which is durable, inspectable, and what the teams who solved this by hand already do.

## Correction (2026-08-30): "would have to fabricate a hash" states a design constraint as an impossibility, and the collector it points at was superseded

The rejection of a `'collect'` policy above says it "would have to fabricate a hash, a receipt, and for a deploy an address". That is stated more strongly than it now holds. The execute guard (ADR 0013) shipped `SkippedExecution` (`packages/rocketh-read-execute/src/index.ts`), a result in which a guarded `execute` returns an evaluation and NO receipt, so "this call produced no transaction" is a representable outcome in the public result vocabulary rather than something a caller has no shape for. The fabrication is therefore a consequence of WHERE the seam sits, inside `broadcastTransaction`, whose contract with `savePendingExecution` / `waitForTransaction` is a hash: it is a design constraint that would have to be paid for, not an impossibility.

The decision itself stands, and nothing above is withdrawn. A DEPLOY still owes dependent code an address for a contract that does not exist, and the load-bearing half of this ADR was never the return contract but the capability-conditional one: a record whose existence depends on whether stdin was a TTY is worse than no record. What is corrected is the register, because an argument recorded as impossible is not re-examined when the surrounding types change, and these did.

The amendment above also closes by pointing at `deferred-transaction-collector` as what writes the collected transactions to an opt-in file. That spec now sits in `work/specs/dropped/` and is superseded by `captured-transactions`, which serves the same need without the seam: a run accumulates every transaction it actually BROADCAST at the broadcast choke point (`env.capturedTransactions`, written by `rocketh --write-transactions <file>`), records a DEFERRED transaction nowhere, and is never read back by rocketh to decide anything. The write-only property this ADR asks for is structural there rather than promised.
