# Unknown-signer seam at the single broadcast choke point; `autoImpersonate` and `onUnknownSigner` are orthogonal

When a privileged call (proxy upgrade, admin action, raw tx, deploy, value transfer) targets an account the deployer key cannot sign for (a Safe multisig, a hardware wallet, an air-gapped key), rocketh surfaces the exact tx to execute out-of-band via a first-class `UnknownSignerError` (`@rocketh/core`), thrown at the SINGLE `broadcastTransaction` choke point in `packages/rocketh/src/environment`. All txs funnel through that function, so one check is enough: hardhat-deploy v1 repeated the same check in five places, rocketh does it once. One caveat found while tasking this, worth recording so it is not re-derived as a surprise: `@rocketh/deploy` performed its OWN `addressSigners` lookup and threw before the transaction reached the choke point, so the "no upstream package needs changing" property held for every path EXCEPT that pre-guard, which had to be routed into the seam separately (see the correction below — this was narrower than it sounds, and the pre-guard is now gone). The error carries `{from, to?, data?, value?, contract?: {name?, method, args}}`, with `contract` populated only when the call originated from an `execute` so the printed message can name the intended function. `contract.name` is OPTIONAL and resolved through the environment's existing `fromAddressToNamedABIOrNull(address)` helper, deliberately NOT by widening `MinimalDeployment` (which is `{address, abi}`) to carry a name: a name is presentation-only enrichment of an error message, and it is not worth a core type change that every `execute` caller would then have to satisfy. The enrichment is nonetheless NOT free of core surface: `broadcastExecution`'s options type is declared on the public `Environment` interface, and the throw happens one level below it in `broadcastTransaction`, which is called with no options at all. Carrying the metadata to the throw site therefore spans the execute call sites, the core interface, the environment and the test harness, which is why it is a separate task from the seam rather than a clause inside it.

The seam keys off an explicit **account signability** classification recorded at environment setup, NOT off the presence of a signer entry: `local` = the resolved signer is `signerOnly` or `wallet`, so we can sign without the node; `node` = a `remote` signer whose address is in `eth_accounts`; `impersonated` = a `remote` signer absent from `eth_accounts` whose impersonation succeeded; `unsignable` = everything else. The state is deliberately NOT named after a single `Signer` member. That union has three variants (`signerOnly`, `remote`, `wallet`), the local-signing one is `signerOnly` (what the `privateKey` and hardware protocols return), and `wallet` is an external wallet provider that nothing in this repo currently constructs. An earlier draft named the state `wallet` for a supposed 1:1 mapping and would have classified every privateKey deployer as unsignable, throwing on ordinary deploys; the union's members are pinned in `CONTEXT.md` so this cannot recur. Precedence is `local` > `node` > `impersonated` > `unsignable`. It was load-bearing when written, because the impersonation pass targeted every named account absent from `eth_accounts`, which included `signerOnly` accounts, so rocketh attempted to impersonate accounts it could already sign for. The same slice narrows that candidate set to accounts whose resolved signer is `remote`, matching what the function's own documentation always claimed, after which the precedence is retained as a defensive invariant rather than a live necessity. The presence test is not viable: a named account declared as a plain address resolves to `{type: 'remote', signer: provider}`, so `addressSigners[from]` is always truthy for a named account and a "no signer" check can never fire for a named Safe. Worse, impersonation is best-effort and silently swallows failure, so without recording its outcome an account whose impersonation FAILED is indistinguishable from one the node genuinely holds. Making signability explicit is what makes the seam correct; it also makes the previously-discarded impersonation result observable.

`autoImpersonate` and `onUnknownSigner` are deliberately kept **orthogonal**. `autoImpersonate` is a NODE CAPABILITY switch (impersonate named unsignable accounts IF the node supports it) and runs BEFORE the seam; if it resolves the account, the seam never fires. `onUnknownSigner: 'throw' | 'auto'` is the policy for accounts that remain `unsignable` after impersonation. `onUnknownSigner` intentionally has no `'impersonate'` value: collapsing the two would conflate "can this node fake signatures?" (a capability) with "what should happen when we genuinely cannot sign?" (a policy). Default is `'auto'`; while no interactive resolver exists, `'auto'` degrades to `'throw'` so CI never prompts or hangs.

`catchUnknownSigner` forces the `'throw'` policy for its wrapped action via an environment-level push/pop frame stack, and the frame is an OBJECT carrying a policy so `unknown-signer-interactive` can push `'ask'` without re-cutting the seam. The stack is dynamic-scope. That is sound for how rocketh runs deploy scripts (sequentially, single-await), but nothing ENFORCES it: a user who runs `Promise.all` of two actions inside one `catchUnknownSigner` leaks the frame to the concurrent action. This is harmless while every policy value resolves to `throw`, and becomes real cross-talk once `'ask'` lands, so it is recorded here as a known limitation rather than asserted away. Relatedly, `catchUnknownSigner` accepts a THUNK only, diverging from v1's `Promise | thunk`: a promise argument has already started executing before the wrapper runs, so there is no moment at which to push the frame, and accepting it would yield a wrapper that silently fails to do its job. The divergence is made loud (a compile error, plus a runtime guard that names the fix) rather than silent. **That frame forces `throw` over `ask`, NEVER over impersonation.** This is the point most easily lost, and it has already been lost once: a wrapped action must not pop an interactive prompt at a user who has explicitly asked to catch the error, but an account the node CAN sign for (including by impersonation) is signable, full stop, and a pushed frame never turns it into a throw. Testing the throw path on a fork is served by `autoImpersonate: false` for the run, and per-account control is parked in `work/notes/ideas/per-call-autoimpersonate.md`. Keeping the frame away from impersonation is also what preserves the mixed run: signable calls broadcast normally inside a wrapper, only the genuinely unsignable one is caught.

## Correction (2026-08-11): the `@rocketh/deploy` pre-guard was narrower than stated, and has been removed

The sentence above overstates the pre-guard's blast radius, and the record is corrected rather than rewritten because the overstatement is itself worth knowing: it is the same mistake the seam's own design avoids.

The pre-guard tested for the PRESENCE of an `addressSigners` entry, not for signability. A named account declared as a bare address always HAS an entry (`{type: 'remote', signer: provider}`), so the guard never fired for the canonical named-Safe spelling — which already reached the choke point. It fired only for a deployer passed as a LITERAL address, which has no entry at all. This is exactly the reason this ADR gives (two paragraphs down) for why the seam cannot key off signer-entry presence; the pre-guard was that same wrong question, one layer up.

`deploy-unsignable-deployer-reaches-seam` removed the guard, so both spellings now behave identically and reach the seam. The removal has one user-visible consequence, recorded here because nothing else states it: with the guard gone, a DETERMINISTIC deploy from an unsignable deployer can cause on-chain side effects before the `UnknownSignerError` surfaces. `getCreate2Factory` runs first, so a missing factory means the pre-signed factory-deployment raw transaction is broadcast (a `raw` transaction, which bypasses the seam entirely), and an under-funded factory deployer means a 21000-gas value transfer is attempted FROM the unsignable account first — so the first error the user sees names the funding transfer, not their deployment. This is absorbed by the idempotent re-run loop, and was accepted deliberately.

Nothing is persisted by this mechanism (no unsigned-tx file, no state), mirroring hardhat-deploy v1 exactly. Idempotency is on-chain-state-driven: the user executes the deferred tx on their Safe, re-runs the idempotent script, and the on-chain state check skips the completed step. A persisted batch, if ever built, belongs downstream in a consumer package (see `explore-unknown-signer-adapters`), not in the core seam, keeping the "one choke point, zero side effects" property that makes the seam auditable.
