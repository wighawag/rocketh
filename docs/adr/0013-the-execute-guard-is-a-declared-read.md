# The `execute` guard is a DECLARED READ, never an opaque predicate

`execute` is the only rocketh primitive with no answer to "is this call still needed?": `deploy` compares bytecode, `deployViaProxy` compares the current implementation address, and `execute` runs whatever it is handed. `execute-state-guard` closes that gap with one option. This ADR records the shape that option takes and the alternatives rejected, because the obvious shape (hand me a boolean function) is the one we did not build, and a future reader will otherwise try to add it back.

**The guard declares WHAT TO READ and how to judge the value, and rocketh performs the read.** Two kinds, discriminated from the first commit so a third is additive rather than a re-cut: `call` (an `eth_call` against an ABI) and `storage` (an `eth_getStorageAt` on a slot). The verdict is expressed either as `satisfied`, a predicate over the DECODED value, or as `equals`, sugar over it for the scalar case. The read stays declarative; only the judgement is a function.

**A whole-guard predicate (`guard: async () => boolean`) was rejected, and this is the load-bearing half.** It is the shape everyone reaches for first, and it is exactly the hand-written `const current = await read(...); if (current !== target)` that the guard exists to replace, relocated inside the call. Its cost is that rocketh learns nothing: the reads happen inside a closure, so there is nothing to report when a step is skipped, nothing for a later collector to evaluate other than by running the closure, and nothing for `state-change-provenance` to consume. Three of the spec's user stories (the evaluation is legible, the guard is evaluable without executing the call, the evaluation is exposed rather than reduced to a boolean) are precisely the properties a closure destroys. `satisfied` keeps the expressive half, since two of the four real topologies cannot be written as an equality at all, while leaving the read declared. If the legibility cost is ever worth paying, a predicate is an additive member of the union, so nothing here forecloses it.

**A `storage` kind is REQUIRED, not an optimisation.** An OZ transparent proxy exposes no getter for its implementation; `@rocketh/proxy` already reads the EIP-1967 slot with `eth_getStorageAt` and says why in a comment. A call-only guard could not express the single commonest upgrade topology there is. Because a slot carries no ABI, a `storage` guard states its own type (`address`, `bytes32`, `uint256`, `bool`), which both decodes the word and supplies the comparison rule the ABI would otherwise have supplied.

**Comparison is keyed off the ABI TYPE, never the JavaScript type.** `address` and `bytes32` fold case (addresses differ by checksum casing and must match across it; a `bytes32` role identifier or salt is a hex value whose casing carries no meaning), `string` does not (it is user data where case is meaningful), bigints never coerce against numbers, and arrays compare elementwise under the same per-type rule. Keying off the ABI is possible only because the read is declared, which is the same property the predicate would have destroyed.

**The guard is OPTIONAL and there is no mandatory mode.** A user who wants no guard can reach the chain by other means anyway, so enforcement at this one option stops nobody determined and taxes everybody compliant. It would also have hit rocketh's own internal `execute` calls in `@rocketh/proxy` and `@rocketh/diamond`, which carry their own comparisons. The double-execution hazard is addressed where it belongs, in the surfaced message and the documentation.

**Which is also why there is NO explicit "this is not observable on chain" marker (decided 2026-08-27).** The spec asked for one, so that the escape hatch would be visible in the script rather than implied by absence. With no mandatory mode, such a marker has zero mechanical effect: it is a code comment with a type. Absence of a guard IS the escape hatch. If a project-level `requireGuards` is ever requested, the marker comes back with it, because only then does it mean something a comment cannot say.

**An unguarded call's type is untouched.** The return type is conditional on the presence of `guard`: without one, `execute` still returns `Promise<EIP1193TransactionReceipt>` exactly as before, so no existing call site changes; with one, it returns the skipped-or-sent result carrying the evaluation. This is what keeps the feature additive for v1 migrants, and it is also the answer to a question `fork-based-discovery-of-pending-privileged-work` flagged against ADR 0012: once "this call produced no transaction" is representable, rejecting a `collect` policy no longer rests on fabrication being impossible for the execute path (it still rests on it for a deploy, and on the counterfactual problem, both untouched).

## Consequences

- The guard is evaluated BEFORE the transaction is built, so a satisfied guard costs one RPC and reaches neither the broadcast choke point nor the unknown-signer seam. It never suppresses that seam either: an unsatisfied guard on an unsignable `from` defers exactly as today. "Is this needed" and "can we sign it" stay orthogonal, for the same reason `autoImpersonate` and `onUnknownSigner` are (ADR 0006).
- A guard that reverts or otherwise throws is FATAL, never "not satisfied". A broken guard that fell through to executing would reintroduce the double-execution hazard the guard exists to remove (ADR 0012).
- Nothing is persisted. Idempotency stays on-chain-state-driven, which is what keeps the v1 no-side-effects parity guarantee true without an asterisk.
- `satisfied` receives the decoded value RAW, so a user who compares addresses inside their own predicate does not get the casing rule that `equals` applies. That trap is documented rather than papered over with a helper, since the helper would be a second comparison vocabulary.
