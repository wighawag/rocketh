# Move the docs site to a SvelteKit docs template of our own

Direction, decided 2026-10-27: the docs site moves off VitePress onto a `template-svelte-docs` derived from the blog template (`template-svelte-tailwind-blog`), built alongside the documentation work rather than ahead of it. The content work (merging the two documentation trees, the Safe walkthrough, checking every page against the code) happens first and stays in plain Markdown, avoiding new VitePress-only syntax, so the switch is mechanical when the template is ready. rocketh.dev switches once the template passes a parity checklist against the real content.

This supersedes the "stay on VitePress" verdict of `docs-site-astro-starlight.md`, which compared VitePress with Starlight only and never weighed a template of our own.

## Why

- The playground (`@rocketh/playground`) is a Svelte component. VitePress (Vue) can only host it as a custom element; a SvelteKit site runs it natively, which also makes editable deploy scripts in the docs (`work/specs/proposed/editable-deploy-scripts-in-the-docs.md`) far simpler.
- One stack: the apps and games use SvelteKit, Tailwind and shadcn, so the docs site exercises the same components and there is one ecosystem to upgrade instead of Vue/VitePress for one site.
- It joins the template tree (`template-svelte` -> `template-svelte-tailwind` -> ...), receives its updates through the existing stem/offshoot-fanout flow, and is reusable for other projects' docs.
- Deriving from the blog gives articles for free (release notes, announcements, tutorials), and keeps Markdown support out of `template-svelte-tailwind`, which apps and games use without needing it.
- A real API reference becomes possible: TypeDoc can emit JSON rendered as pages of the same site. Today TypeDoc is only a local `gen-docs` script in `@rocketh/node` and nothing is published.

## Spike, 2026-10-27

Throwaway branch `spike/rocketh-docs` of `wighawag/template-svelte-tailwind-blog` (commit `3255a94`, with a `SPIKE.md`): the 38 real pages of `documentation/` and `hardhat-deploy/` on the blog template, about 300 added lines (the VitePress config and theme are about 270).

Worked:

- All 38 pages compile and pre-render, after handling VitePress `{#custom-id}` heading anchors (mdsvex otherwise reads `{#` as Svelte block syntax and fails the build).
- `::: tip` / `warning` / `danger` through the blog's container plugin, plus a pre-pass, because that plugin only sees containers separated by blank lines and VitePress also allows the compact form.
- `::: code-group` as CSS-only tabs; Shiki highlighting with light and dark themes.
- Sidebar generated from the folder tree; on-this-page TOC from h2/h3; heading anchors.
- Existing site-absolute links resolve unchanged when the docs are mounted at the site root.
- Dead-link checking for free from SvelteKit's prerender crawl. It found three real broken links on the live site (fixed alongside this note).
- Pagefind search over the static build (37 pages, about 1 MB index), results rendered in-page.
- The playground loads and registers with no page errors.

Not done, and the real cost:

- Sidebar ORDER: autogenerated is alphabetical. Needs an `order` frontmatter field per page or a small nav file.
- Styling: the blog's dark theme and typography make body text too dim, and inline code shows its backticks. Design work, where shadcn's components and theme help.
- Missing pieces: the home page hero (`layout: home`), mobile menu, dark-mode toggle, previous/next links, "edit on GitHub", copy buttons on code blocks, a styled search box.
- Search works only on the built site, not under `vite dev`.
- mdsvex: an old remark parser (why the blog hand-rolls containers), and a `{` in plain prose (outside code) breaks a page, which every docs author would have to know. A separate unified/remark pipeline is the more durable choice; decide it in the template, early.
- Build size about 14 MB, mostly the playground's in-browser EVM, which the VitePress build carries too.

## Open questions

- Template tree: does the blog become a child of `template-svelte-shadcn` (so the docs template, a child of the blog, gets shadcn too), or does the docs template copy the few shadcn components it needs?
- mdsvex or a unified/remark pipeline.
- The parity checklist that decides the switch: the "not done" list above, plus whatever the docs audit adds.
