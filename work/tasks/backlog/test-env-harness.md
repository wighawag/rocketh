## What to build

This is the EXPAND step of an expand → migrate → contract sequence (`TASKING-PROTOCOL.md` §3a). Add a new harness BESIDE the existing `createMockEnvironment`; change no existing test, delete nothing. The migration and the removal are separate tasks.

The problem it solves: `createMockEnvironment` hand-builds an `Environment`-shaped object literal and reimplements `broadcastExecution` / `broadcastDeployment` so they call the provider directly. So no test that uses it exercises `createEnvironment` setup or the real broadcast path — no account resolution, no `eth_accounts`, no impersonation, no `broadcastTransaction`. (The only exceptions in the repo are `packages/rocketh/test/addressSigners-casing.test.ts`, the minimal regression that landed with `09ea46d`, and `loadDeploymentsFromStore.test.ts`, which imports one function from the module.) Every integration test otherwise exercises a parallel fake, which is the opposite of what the integration-tests-as-documentation convention promises.

**Who this harness is for.** The extension packages: `@rocketh/unknown-signer`, `@rocketh/deploy`, `@rocketh/proxy`, `@rocketh/diamond`, `@rocketh/read-execute`. It is deliberately NOT for `rocketh`'s own tests: `rocketh` must not depend on `@rocketh/test-utils`, because this harness makes test-utils depend on `rocketh`, and the reverse edge would close a project-graph cycle against `nx`'s `dependsOn: ["^build"]`. Tests for `rocketh` internals build a real environment locally instead, as `addressSigners-casing.test.ts` does. That split is deliberate; do not "unify" it by adding the reverse dependency.

Add `createTestEnvironment` to `@rocketh/test-utils`:

- **Async**, returning a genuine environment: resolve a config and execution params with the exported `resolveConfig` / `resolveExecutionParams` (the latter also needs a chain id, for which `getChainIdForEnvironment` is exported and probes `eth_chainId`), call the exported `createEnvironment(config, executionParams, deploymentStore)`, and hand back its `external` environment (keeping `internal` reachable for anything that needs it). It is async because `createEnvironment` is; being a NEW export, that costs no migration.
- **A way to express a locally-signing account.** Account definitions are resolved through `userConfig.signerProtocols`, and nothing populates it, so without a registered protocol a 66-character `0x` private-key definition silently resolves to undefined (note the `if (privateKeyProtocol)` guard in setup). Register the REAL shipped protocol, `privateKey` from `@rocketh/signer`, rather than hand-rolling a stand-in, and/or let callers supply one through the generic config pass-through, since `signerProtocols` is part of `UserConfig`. Precedent: `09ea46d` added `@rocketh/signer` as a devDependency of `rocketh` for exactly this purpose in a test. Note `@rocketh/signer` is NOT currently any kind of dependency of `@rocketh/test-utils`, and adding one to a published package is an ask-first decision under `AGENTS.md`: state your intent explicitly, whether that is a devDependency used only by the harness's own tests with runtime registration left to the caller, or a declared dependency with that widening accepted. Without a route to `signerOnly` there is no way to produce a locally-signing account.
- **A test home for this package.** `@rocketh/test-utils` currently has no `test/` directory, no `vitest.config.ts` and no `test` script, and the root config collects projects from `packages/*/vitest.config.ts`. So tests added here today would SILENTLY not run and `pnpm test` would still report green. Add the `vitest.config.ts` and the `test` script alongside the harness, matching a sibling package, and confirm the root `pnpm test` file count actually rises.
- **A Map-backed `DeploymentStore`** implemented here. Note `@rocketh/web`'s `createEmptyDeploymentStore()` is NOT an in-memory store despite the name: its bodies are commented out, so writes are discarded, `readFile` returns empty, `listFiles` returns `[]`, and nothing survives a second environment creation.
- **Provider defaults covering what real setup calls** and the current defaults omit: at minimum `eth_accounts`, the genesis block probe (`eth_getBlockByNumber`), `eth_getTransactionByHash`, `eth_call`, and `hardhat_impersonateAccount`. Reuse the existing default-response mechanism rather than forking a second one. Give the default receipt a per-transaction incrementing `contractAddress` (see the pitfall below).
- **A documented RESULT shape and a per-test provider lever.** Return the mock provider handle alongside the environment, at value AND type level, so a test can set a canned response and inspect requests: existing tests already use `provider.setResponse` and a `ReturnType<...>['provider']` type reference, the migrations need it, and `unknown-signer-integration-scenarios` needs per-slot `eth_getStorageAt` answers to drive a proxy upgrade and to move on-chain state between runs. Omitting this would repeat, one level down, the missing-lever problem that already blocked this task once.
- **Options expressive enough to describe an unsignable account**, which is the whole point: named accounts in the real config shape (an index into `eth_accounts`, a private key, a protocol string, or a bare address), which addresses the node actually holds, whether `hardhat_impersonateAccount` succeeds or fails, and `autoImpersonate`.
- **A GENERIC pass-through too**: a partial `UserConfig` (including `chains[id]`) and partial execution params merged into what is resolved. Downstream tasks need settings this task cannot enumerate in advance — the first, `unknown-signer-broadcast-seam`, must exercise an `onUnknownSigner` precedence chain of execution param over chain config over default — and their scope fences exclude `@rocketh/test-utils`. Without a generic lever they are stranded, or they breach their fence.
- **Casing: the old trap is gone, but the remaining asymmetry is deliberate and should be asserted.** `addressSigners` keys are now lowercased by `createEnvironment` (commit `09ea46d`), so checksummed input no longer breaks a broadcast. What remains BY DESIGN is that the address VALUES in `namedAccounts` and `unnamedAccounts` are un-normalised, because they are user-visible and reach deployment records and frontend exports where EIP-55 checksums are an integrity feature. The existing default named-accounts constant is checksummed, which is correct and should stay. Have the harness's own tests assert that `namedAccounts` values keep their checksum while `addressSigners` keys are lowercase, so a later tidy-up cannot quietly break the fence.
- **A small polling interval**, so a mis-mocked receipt fails fast: receipt waiting recurses at the configured interval with no deadline, so a receipt missing `blockHash` HANGS rather than failing, and the test dies on the runner's timeout if it has one.
- **`rocketh` as a `peerDependency` plus `devDependency`**, the pattern `@rocketh/web` already uses, rather than a hard runtime dependency. There is no cycle (`rocketh` does not depend on test-utils). Note the ripple: `@rocketh/test-utils` is a devDependency of `rocketh-deploy`, `-proxy`, `-diamond` and `-read-execute`, so a new peer dependency touches those four manifests.

**Explicit NON-GOAL: no stateful chain simulation.** The provider answers the calls real setup and the real broadcast path make; it does not model chain state. Keep responses canned or per-test configurable, and do not grow an in-memory chain. The reason is scope discipline, not a specific hazard: a harness that starts simulating state acquires an open-ended obligation to keep simulating it correctly, and every test then depends on a second, unspecified EVM. If a later migration genuinely needs more, that task scopes it explicitly.

**The known concrete pitfall is the receipt, not `eth_getCode`.** The current default `eth_getTransactionReceipt` returns the SAME `contractAddress` for every transaction, while the real environment takes a deployment's address from `receipt.contractAddress`. So under a real environment, every deployment in one test collapses onto one address, which breaks anything deploying more than one contract (a diamond deploys many facets plus a proxy). Give the default receipt a per-transaction incrementing `contractAddress`. Note for the avoidance of doubt: `@rocketh/proxy` and `@rocketh/diamond` do NOT branch on `eth_getCode` — they branch on `env.getOrNull(name)`, the in-memory deployment record — so provider statefulness is not what decides their upgrade-versus-fresh path.

## Acceptance criteria

- [ ] `createTestEnvironment` is exported from `@rocketh/test-utils`, is async, and the environment it returns IS the object `createEnvironment` returned (an identity check, not a spread or a wrapper).
- [ ] No method on the returned environment is a reimplementation of production logic.
- [ ] `@rocketh/test-utils` has a `vitest.config.ts` and a `test` script, and the harness's own tests demonstrably RUN from the root `pnpm test` (the reported file count rises).
- [ ] A test asserts something that can ONLY pass through the real path — for example that signer selection follows `addressSigners` (a `signerOnly` account signs then sends raw, a `remote` one uses `eth_sendTransaction`), or that `evm_mine` is emitted when `autoMine` is on. Merely observing `eth_sendTransaction` params is NOT sufficient: an existing test already does that against the old fake. `packages/rocketh/test/addressSigners-casing.test.ts` is useful PRIOR ART for the assertions. Do NOT delete or migrate it: under the dependency split above it is the sanctioned pattern for `rocketh`-internal tests, and it cannot use this harness.
- [ ] `TESTING.md` is reconciled: it already documents `createTestEnvironment` in three places for a function that does not exist. Making it "true" means more than the name matching — all three snippets call it SYNCHRONOUSLY and one destructures `{env, accounts}`, so they must be updated to `await` it and to match the actual result shape, or the samples stay broken. `CONTEXT.md` and `AGENTS.md` must end up consistent with it too (`AGENTS.md` still points agents at `createMockEnvironment`).
- [ ] `namedAccounts` values keep their checksum while `addressSigners` keys are lowercase (explicit assertion, protecting the fence held in `09ea46d`).
- [ ] The harness's OWN tests drive `env.broadcastExecution` and `env.broadcastDeployment` and reach the real `broadcastTransaction`. They must NOT import `@rocketh/deploy` or `@rocketh/read-execute`: both already devDepend on `@rocketh/test-utils`, so importing them here would close a second project-graph cycle and break `pnpm build`. That `deploy` / `execute` / `tx` work end to end against the harness is proven by the two migrate batches, which live in packages that may depend on it.
- [ ] Options can express: an account the node holds, an account with local signing material, an account the node does NOT hold, impersonation succeeding, impersonation failing, and `autoImpersonate` on/off — PLUS the generic partial `UserConfig` / execution-params pass-through.
- [ ] Creating an environment and running a deployment produces no unmocked-provider-method warning and no chain-config console noise.
- [ ] The deployment store is Map-backed and touches no filesystem; two sequential environments on the same store see the same deployments.
- [ ] `createMockEnvironment` is UNCHANGED and every existing test still passes untouched — this task adds, it does not migrate.
- [ ] The result exposes the mock provider handle (value and type) so tests can set canned responses and inspect requests, and the default receipt yields a DISTINCT `contractAddress` per transaction (a test deploying two contracts gets two addresses).
- [ ] A `signerOnly` account can actually be constructed through the harness (a `privateKey` protocol is registered or suppliable), and the signer-selection criterion above is demonstrated with one.
- [ ] `AGENTS.md` points new tests at `createTestEnvironment` (the old one is removed in a later task, so both are documented for now, with the reason). Note two later tasks also edit `AGENTS.md` (`unknown-signer-package` adds the new package, `remove-legacy-mock-environment` drops the old mentions); they touch different sections, so keep this edit tightly scoped to avoid a needless conflict.
- [ ] A changeset accompanies the new export.
- [ ] `pnpm typecheck`, `pnpm build` and `pnpm test` pass across the workspace.
